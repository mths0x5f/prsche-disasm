# Run 286: first two original startup constructors

The [read-only preflight](summary.json) checks original `Porsche.exe` bytes and its writable `.data` constructor table. Its first two nonzero slots run `004035e0` (20 bytes) before `00403600` (19 bytes). The first copies bit pattern `0x00800000` to the initially zero four-byte cell `005e6724`. The second executes x87 `FLD` of original `1.0f` at `005b24a8`, `FDIV` by the float in `005e6724`, then `FSTP` into the distinct four-byte cell `005e6720`. The exact-power result derives to `0x7e800000`; this is a mathematical result from the instructions, not a new original runtime capture.

The PE contains exactly two direct literal references to `005e6724`: that write and the division read. It contains one to `005e6720`: the store. No direct later read of the result cell or interior `+1..+3` literal was found. Computed or indirect accesses remain possible. Neither constructor has an indexed function range, registry owner or matching recovered-source definition; Run274 has no exact symbol owner. This narrows the earlier startup concern: these cells are proven constructor state, but their effect on a later game path is **not** proven.

A minimal isolated proof packet, if needed, would own two separate four-byte cells and reproduce only these two callbacks in the recorded order, comparing x87 result bits and relevant FP state against original execution. It must not stand in for the rest of the original constructor table or CRT. No production integration is warranted from the direct-consumer evidence alone. [Validation](validation.json) pins the input and audit hashes. Run286 compiled and executed nothing.
