# Автоматизация восстановления

Цель — сокращать ручную работу между восстановлением исходников и первым запуском
игры, сохраняя проверку по оригинальному бинарнику.

Источник идеи: [ps2-web-recomp](https://github.com/snuri00/ps2-web-recomp),
особенно [scripts/port.sh](https://github.com/snuri00/ps2-web-recomp/blob/main/scripts/port.sh).
Там машинный код переводится в C++, пробные запуски записывают недостающие точки
входа, затем перевод и сборка повторяются. PS2 runtime обслуживает оборудование.
README автора сообщает о GT4 и God of War II; локально мы эти игры не запускали.

## Ближайший цикл для Porsche

1. Собирать связанные доказанные изменения одним compiler batch; сохранять
   команду, exit code, время и лог до разбора результатов.
2. Объединять готовые пакеты одной линковкой. Повторно использовать COFF,
   symbol snapshots и SHA-проверки; не повторять компиляцию из-за ошибки отчёта.
3. Из фактических неразрешённых зависимостей получать следующую очередь автоматически:
   существующий canonical/WIP owner, неверный ABI, отсутствующее тело, данные или
   платформенный provider. Приоритет учитывает число consumers и размер тела.
4. Перед новой реализацией проверять accepted и WIP owners, включая interior ranges.
   Подключать доказанное существующее C++-тело. Run240 показывает механическое
   извлечение точных canonical-фрагментов без повторной реализации алгоритма.
5. После появления игрового EXE собирать реальные косвенные точки входа, переходы
   и отказы providers при запуске. Сравнивать входы/состояния/выходы с оригиналом.
   Текущая диагностическая DLL-линковка не является запуском игры.

Run241 проверяет include roots по реально выполненной compiler command.
Run243 объединяет готовые изменения. Run245 формирует очередь из результатов
линковки: 442 неразрешённых имени дали 440 задач, 17 уже разрешённых строк исключены.

Команды и границы проверки сохраняются в README соответствующих runs.

### Контракт готового пакета

Collector241 ожидает `original_sha256`, `compiler_sha256`, `input_sha256` и
`validation.json`, который фиксирует SHA конкретного summary. Для данных нужны
`kind: original-writable-data` или `original-readonly-data` и `support_objects`;
точные bindings публикуются отдельным `proven-link-contract` пакетом.

Collector268 также принимает `native-platform-provider`: точные existingplatform
fragments,actualcode/importsymbols иobservedcompilerclosure. Такой code считается
support,не recoveredgamefunction. Data/binding support не может иметь executable
COFF sections; namespaceddata допускается с той же проверкой. Run268 проверил два
Win32critical-section adapters, Run269 закрыл их actuallinknames иrawfreebinding.

Старые manual/corpus/index файлы могут быть SHA-pinned завершёнными пакетами.
Новый navigation material сохраняется отдельно в `research/binary-index/supplemental`.
Run271 использует `candidate_entry_va`, `entry_status: unproved`, без `entry_va`:
это препятствует автоматическому принятию candidate как доказанной функции.

Actual compiler/link/native receipts и логи сохраняются до разбора результата;
файлы receipts тоже включаются в closure. Команду и exit нельзя восстанавливать
по наличию COFF. Для quoted include roots нужны фактическая `/I` команда и receipt.
`/sourceDependencies` сохраняет параллельную `/MP` сборку; `/showIncludes` её отключает.
Новые отчёты и исходники записываются в UTF-8/LF до вычисления SHA. Исторические
зафиксированные байты сохраняются точно. Run255 показывает metadata-only adapter
для старого формата без повторной компиляции и без правки завершённых пакетов.

## Отдельный эксперимент с автоматическим переводом x86 в C++

Run246 проверил первый малый набор: `00590290`, `00590070`, `004930f0`.
Из 76 точных PE-байтов / 28 инструкций автоматически получен C++ с явными
регистрами, операциями памяти, флагами и прямыми переходами между метками.
Во время исполнения генерируемого C++ инструкции не декодируются.
375 808 сравнений с оригинальными x86-телами прошли: EAX/ECX/EDX и сохраняемые
регистры, относительное изменение ESP при RET/RET8, CF/ZF/SF/OF и записи в память.
Независимый аудит проверяет PE, повторную генерацию C++, COFF-оракулы и receipts.

Один compiler batch из четырёх TU занял 1,686 с; native-стенд — 1,185 с.
Первый link выявил зависимость от memcpy; те же COFF перелинкованы с CRT,
без повторной компиляции. Это существующие владельцы из основного восстановления:
новых принятых функций нет, игровая сборка и реестр не менялись.

Покрытие переводчика на очереди отсутствующих тел проверяется отдельно от трёх
изученных примеров. Эффект на скорость восстановления больших частей игры пока
не измерен.

Run252 уже измерил все 85 отсутствующих тел текущей очереди: ни одно целиком не
поддерживается набором Run246; 80 содержат CALL. По этому результату Run253 добавил
внешний прямой JMP на трёх коротких wrappers. 18 432 native-сравнения подтвердили
состояние в точке передачи управления, включая входной ECX и неизменённый стек.
При отсутствии VM-цели dispatcher останавливается с `MissingEntry` и записывает
исходный target PC. Три адреса в журнале имеют `provenance: isolatedVMpilot`;
это пропуски экспериментального VM backend, не утверждение о недостающих native
телах и не запуск игры. Целевые callees остаются незавершёнными.

Run257/258 реализовал это расширение: PUSH/POP, арифметику ESP и CALL/RET с проверкой
оригинального возвратного PC. Три зарегистрированные оригинальные цепочки
(6 тел / 104 байта / 34 инструкции) прошли 36 864 native-сравнения регистров,
CF/ZF/SF/OF, памяти объектов и стека. MissingEntry, испорченный return PC и
исчерпанный instruction budget дают явную остановку. Сборка 8 TU одним /MP6
batch заняла 2,243 с, native-стенд — 2,064 с; независимый аудит 59 pins прошёл.

Run260 повторно измерил прежнюю очередь: 25 из 85 тел теперь переводятся целиком
синтаксически. Это не доказательство поведения этих 25 функций. Первый отказ
в остальных 60 часто связан с MOVSX, OR, shifts, дополнительными условиями
переходов и x87. Следующий шаг — проверять инструкции на native fixtures и
собирать связанные оригинальные диапазоны, сохраняя остановку на неизвестных
callees/imports. Полное ускорение до игрового EXE пока не измерено.

Run262 отдельно проверил ранее неисполненные CPU corners:15 744synthetic native
cases для byte/word/32 ADD/SUB/SBB/NEG, partialregister views, PUSH/POP ESP,
POP[ESP], indirectCALL[ESP]/JMP[ESP+4].19COFForacles/70B/0relocations совпали;
28pins audit PASS. Это проверка инфраструктуры CPU, новых функций игры здесь нет.
Кодовые указатели/return PC нормализуются только в явно заданных слотах стенда.
Семантику инструкций и флагов сверять с
[Intel SDM](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html),
а поведение конкретной функции — с оригинальным Porsche.exe.

Критерии эксперимента:

- Генератор получает инструкции из проверенных PE-байтов. Неподдержанная инструкция
  или неизвестная точка входа даёт явный диагностический результат.
- Нет приблизительных функций, вызова оригинального машинного кода как игровой
  реализации или незаметного fallback, скрывающего пробелы перевода.
- Сравниваются регистры, существенные флаги, стек и изменения памяти, включая
  граничные значения. Компиляция сама по себе не является приёмкой.
- Фиксируются затраты на перевод и проверку относительно нынешнего восстановления.
  Win32 imports, callbacks и указатели на код требуют отдельных контрактов.
- Эксперимент остаётся в `local/experiments`, с версионированным генератором и отчётом.
  Его результат определит применимость к большему числу функций. Существующие
  проверенные owners и план дальнейшего структурного описания/Rust-порта сохраняются.

Пока не реализованы imports/callbacks, полный guest memory loader, x87/SSE,
PF/AF/неопределённые флаги, исключения и сбор реальных игровых runtime misses.
Неподдержанные инструкции, оборванные байты и переходы мимо границ инструкций
отклоняются до компиляции. Пробелы типов и зависимостей нельзя считать закрытыми потому,
что другая архитектура процессора уже успешно перекомпилирована в чужом проекте.
